## 3. SQLite migrationをSingle Source of Truthへ寄せる

### What

`App.tsx`と`useDatabase.ts`に重複していたランタイムCREATE/DROPを削除し、Version 2 migrationへ追加テーブルDDLを集約した。APIキーは引き続きkeyringのみで管理し、DBには保存しない。

### Why

アプリ起動処理でテーブルを削除・再作成すると、既存データを失う危険がある。また複数箇所にDDLがあるとスキーマ差分が発生するため。

### Where

- `src-tauri/src/lib.rs`
- `src/App.tsx`
- `src/hooks/useDatabase.ts`

## 詰まったポイントと対策

| 事象 | 原因 | 対策 |
|---|---|---|
| 既存テーブルへFKを追加できない | SQLiteの`CREATE TABLE IF NOT EXISTS`は既存テーブル定義を更新しない | データ保持を優先し、追加FKは将来のVersion 3整合化migrationへ分離 |
| LangChainチャンクが869KB | Coreと全プロバイダーSDKを単一manual chunkへ強制していた | SDKを動的importし、プロバイダー別チャンクへ分割 |
| DeepSeekサブエージェントの一部返却が遅延 | 初期タスク範囲が大きく、必須文書の読み込みと調査に時間を要した | タスクを5分単位へ再分割し、成果物契約を1〜2ファイルに限定 |

## 5. Holistic code review（2026-08-11）

### What

MCPグラフ分析と、Standards（AI_RULES / DESIGN_SYSTEM）・Spec（DESIGN_SPEC / DATA_SCHEMA）の2軸レビューを実施した。UI、API/LLM、Rust/Tauri、仕様・異常系をDeepSeek V4 Flashで独立確認した。

### 重要な学び

- SQLiteのFKを正式化した後は、以前の仮IDや遅延保存が実行時バグへ変わる。`api_usage_logs.meeting_id=999` は、会議行を先に作成して実IDを伝播しない限り利用できない。
- セキュアストレージを使っていても、レンダラーへのキー展開、URLクエリ、CSP無効、広域fs/sql権限が組み合わさると漏洩・改変面が残る。境界ごとに最小権限を確認する。
- 4層マージは順序だけでなく、学習履歴の件数・並び・失敗時の停止動作まで仕様としてテストする必要がある。
- DESIGN_SYSTEMのトークン定義が存在するだけでは準拠にならない。実値、Tailwind上書き、`avatar-pixel`の適用対象まで確認する。

### 検出した優先課題

P0は会議中利用量ログのFK不整合、P1はCSP/権限、APIエラーの永続化、APIキーゲート、学習履歴制限、デザインSSoT逸脱。詳細は `docs/code_review_report_20260811.md` を参照する。

## 6. レビュー反映とP0是正（2026-08-11）

- 設計上の親子関係をSQLiteのFKだけに任せず、「親行作成 → 実ID確定 → 子行保存」の順序をアプリ側でも明示する必要がある。`MeetingScreen` は会議開始時に `meetings` 行を作成し、`meeting_id=999` を廃止した。
- Phase 1を「画面が動く」だけで完了扱いにせず、仕様の状態機械・永続化・ユーザー確認フローを別タスクとして管理する。`ROADMAP.md` と `REVIEW_ACTION_REGISTER_20260811.md` にP0/P1/P2を登録した。
- AIが候補を生成することと、ユーザーが決定を確定することを設計書で分離する。決定事項の自動学習はユーザー確認済みデータだけを対象にする。

## 7. セッション終了時の引き継ぎ（2026-08-11）

### What

Holistic reviewの所見を設計書・進捗管理表へ反映し、SQLite Version 3のFK強制によって露呈した会議ID不整合を修正した。`MeetingScreen` は会議開始時に親行を作成し、実IDが確定するまで発言ループを開始しない。利用量ログには仮IDを渡さず、停止・サマリー時に親行を終了する。AI生成の決定事項を、ユーザー確認前に `member_learnings` へ登録する経路も停止した。

### Why

SQLite V3で外部キーが有効になると、画面上は動いていた仮保存が実行時エラーへ変わる。親子保存順序と「AI候補／ユーザー確定」の境界を、コードと設計の双方で固定する必要があるため。
